## Task 1: WASM endpoint with the Spin SDK

### Scaffold

The project was generated by the template, not written by hand:

```
$ mkdir -p wasm && cd wasm
$ spin new -t http-go moscow-time --accept-defaults
```

Afterwards only four things changed: the handler body, the route, the application description,
and the componentize-go version pinned in go.mod.

### Toolchain note

The lab text was validated with Spin 3.4, TinyGo 0.41 and SDK v2. The lab also says to scaffold
from the current template for whatever Spin version is installed, and that is what this project
does. The Spin 4.2.1 template for Go no longer uses TinyGo. It uses SDK v3 and builds the
component with componentize-go, which runs on the standard Go toolchain. The Spin v4
documentation states the same: Go 1.25.5 or above is required, and TinyGo is no longer needed.

The TinyGo path was tried first and does not work on this toolchain. TinyGo 0.43 with SDK v2
builds a module that traps on every request inside the SDK, before the handler runs. Spin answers
HTTP 500 with an empty body, and the wasm backtrace ends in runtime.setupDeferFrame. That is part
of the defer and recover machinery TinyGo reworked in 0.42, and an export entered through
buildmode=c-shared has no goroutine state for it to attach to. The current template avoids the
problem because it does not use TinyGo at all.

The build command in spin.toml is therefore the one the scaffold generates. Everything else in
requirement 1.3 is unchanged: the trigger is routed at /time and allowed_outbound_hosts is empty.

### main.go

```go
package main

import (
	"fmt"
	"net/http"
	"time"

	spinhttp "github.com/spinframework/spin-go-sdk/v3/http"
)

// Moscow is UTC+3 all year round: Russia stopped changing the clocks in 2011.
// The zone is built by hand rather than with time.LoadLocation, because a WASM
// build carries no tzdata and the lookup would fail at runtime.
var moscow = time.FixedZone("MSK", 3*60*60)

func init() {
	spinhttp.Handle(func(w http.ResponseWriter, r *http.Request) {
		if r.Method != http.MethodGet {
			w.Header().Set("Allow", "GET")
			w.WriteHeader(http.StatusMethodNotAllowed)
			return
		}

		now := time.Now().In(moscow)

		// The body is written with fmt and %q rather than encoding/json. There
		// are five fields, none of them need escaping beyond what %q does, and
		// a WASM build is better off without the reflection an encoder drags
		// in.
		w.Header().Set("Content-Type", "application/json")
		fmt.Fprintf(w,
			`{"zone":"Europe/Moscow","utc_offset":"+03:00","unix":%d,"iso":%q,"hour_minute":%q}`+"\n",
			now.Unix(),
			now.Format(time.RFC3339),
			now.Format("15:04"),
		)
	})
}

// main is required by the compiler but never runs. The host calls the handler
// registered in init.
func main() {}
```

### Design questions

**a) Browser WASM against server WASM.**
A build for js/wasm only runs inside a JavaScript host. It needs the wasm_exec.js glue file, and
it reaches the outside world through the syscall/js bridge: DOM, fetch, timers. A build for
wasip1 has none of that. There is no DOM, no fetch, no JavaScript bridge, and no full set of OS
system calls. What it gains is a host interface that does not need a browser. WASI gives stdio,
environment variables, a clock, and file and socket handles when the host grants them. The same
artifact then runs under wasmtime, Spin, a containerd shim, or an edge platform. The artifact is
also much smaller, because the JavaScript glue and the parts of the runtime that serve it are
gone.

**b) Why the build command needs buildmode=c-shared.**
A default wasip1 build produces a command module. It exports \_start, the host calls it once, main
runs, and the module exits. Spin needs the opposite shape: a reactor module that is instantiated
and then kept callable, so the host can invoke the HTTP handler export for each request. The flag
buildmode=c-shared makes TinyGo emit \_initialize plus the exported functions instead of \_start.
Without it the module has nothing for the host to call, so Spin returns HTTP 500 and the component
log stays empty. With componentize-go the flag is not needed, because the tool emits a WebAssembly
component whose wasi-http handle-request export is part of the component interface.

**c) The capability model against Docker network isolation.**
Setting allowed_outbound_hosts to an empty list means the component is never given an outbound
network handle. This is deny by default: the component cannot ask for a capability it was not
granted, because there is no system call to ask with. Access is granted per component and per
host, so one component in a manifest can be allowed to reach one API while its neighbour reaches
nothing. Docker with network none works at a different level. It removes the interfaces from the
container network namespace, so the process still has every network system call, it simply has no
route. It is also all or nothing: to allow one host and deny the rest you need firewall rules or
a proxy outside the container. The WASM model expresses the same policy in the manifest, and the
runtime enforces it above the kernel.

**d) TinyGo stdlib gaps.**
Two gaps shaped the handler. The first is time zone data. TinyGo embeds no tzdata, so
time.LoadLocation("Europe/Moscow") fails at runtime. The handler builds the zone with
time.FixedZone instead, which is correct here because Russia has not changed its clocks since
2011. The second is reflection. encoding/json over a map of string to any leans on reflection
that TinyGo supports only partly, so the body is formatted with fmt and the %q verb. The final
build uses componentize-go and the full Go toolchain, where reflection is not a problem, but
neither choice was reverted. The tzdata gap applies to any WASM build unless time/tzdata is
imported on purpose, and the hand written body keeps the artifact smaller.

## Task 2: Perf comparison against the Lab 6 container

### How the numbers were taken

The script wasm/measure.sh produces everything below in one run, and its raw output is in
wasm/perf. Both runtimes serve at the same time: spin up on port 3000 and the Lab 6 container on
port 8081. Warm latency is 50 hyperfine runs per target after 5 warmup runs, as the lab asks.
Cold start spawns each runtime from scratch and polls until the first HTTP 200, five samples
each, and reports the median.

One point about the warm numbers. hyperfine times a whole curl process, and the fastest run
against either target was about 4.6 ms, nearly all of it process startup. That is far more than
either server spends on a request, so the hyperfine columns mostly measure curl. To separate the
server, the script also sends 50 requests from one curl process and reads time_total for each.
Both measurements are reported.

### Results

| Dimension | Lab 6 Docker | Lab 12 WASM/Spin |
|------------------------|-------------:|-----------------:|
| Artifact size | 15.8 MB | 4.60 MB |
| Cold start (p50) | 135.6 ms | 77.5 ms |
| Warm latency p50 | 5.69 ms | 5.06 ms |
| Warm latency p95 | 7.05 ms | 5.86 ms |

Artifact size is the uncompressed on disk size that docker images reports, against main.wasm on
disk. The compressed layers of the image are 4.43 MB, which is close to the wasm file, but the
image needs 15.8 MB of disk once it is pulled.

### Server side latency, measured without process startup

| Measurement | Lab 6 Docker | Lab 12 WASM/Spin |
|-------------|-------------:|-----------------:|
| p50 | 0.281 ms | 0.641 ms |
| p95 | 0.435 ms | 0.873 ms |

This is the more useful comparison of the two, and it points the other way. The Go process in the
container answers in about 0.28 ms. Spin takes about 0.64 ms, roughly twice as long, because it
creates a fresh WASM instance for every request. That per request instantiation is part of what
makes the model safe to share between tenants, and it still costs well under a millisecond.

### Design questions

**e) What dominates each cold start.**
For the container, almost all of it is setup that happens before the application starts. The CLI
talks to the daemon. The daemon creates the container, mounts the overlay filesystem, sets up
the namespaces and cgroups, creates the veth pair and publishes the port. The Go binary itself
starts in a few milliseconds. For Spin, the cost is starting the spin process, parsing the manifest,
reading the 4.6 MB module from disk, and letting wasmtime compile and instantiate it. There is no
filesystem to mount and no network namespace to build. Inside an already running Spin the picture
changes again. The module is loaded once, and a new instance per request costs a fraction of a
millisecond. That is the single digit number the reading quotes.

**f) Where each one fits.**
WASM is clearly better where cold start and artifact size decide the user experience, and where
many small units of untrusted code share one machine. Edge handlers at hundreds of points of
presence, plugin systems inside a larger product, and multi tenant request handlers with spiky
traffic all fit. A single artifact also runs on any CPU architecture, so there is no per
architecture image to build. Docker is still the right answer for long running stateful services.
It also wins for anything with a heavy database client or another large dependency. The same
goes for anything that needs arbitrary OS packages or system calls, because a WASM guest has no
shell and no system calls beyond what WASI defines. Tooling matters too. Debuggers, profilers
and base images for containers are mature, and the WASM equivalents are still rough.

**g) Multi tenant safety.**
The attack that gets much harder is a container escape through the shared kernel. A container
process makes real system calls. A bug in that system call surface can be reached from inside
the container, and it can be used to break out to the host or to another tenant. A WASM guest
makes no system calls at all. It can only call the host functions it was given, and the manifest
in this lab gives it none beyond the HTTP handler. Its memory is a separate linear buffer with
bounds checks, so a stray or crafted pointer cannot read host memory or another tenant's data.
Concretely, reading another tenant's files or /etc/passwd is not a matter of permissions here:
there is no filesystem handle to use, so there is nothing to attack.
